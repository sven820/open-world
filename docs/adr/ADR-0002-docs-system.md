# ADR-0002：建立项目文档体系

- 状态：accepted
- 日期：2026-11-17
- 决策人：项目所有者

## 背景

项目此前无文档管理体系：架构思考散落在对话中，设计文档（如 walkstreet/docs）与代码同级放置、无索引、无状态管理。随着 AI Agent 平台化开发启动（多阶段、跨模块、长期演进），需要可追溯的文档中枢。

## 决策

1. 建立仓库根级 `docs/` 目录作为唯一文档中枢，分类：`architecture/`（架构与调研）、`design/`（研发设计）、`requirements/`（需求分析）、`plans/`(研发计划)、`testing/`（测试用例）、`adr/`（架构决策记录）
2. 采用 **ADR（Architecture Decision Record）机制**：每个重大技术决策一篇编号文档，只增不改；推翻决策时新写 ADR 并将旧篇标记 deprecated
3. 模块级文档（walkstreet/docs 等）保留原位，由 `docs/README.md` 全局索引统一收录
4. `docs/README.md` 是强制索引：任何文档新增/移动必须回此登记
5. 文档与代码同仓库提交——文档即真相，实现偏离设计时先改文档

## 备选方案（否决理由）

| 备选 | 否决理由 |
|---|---|
| 不建体系，文档散落在对话记录与模块目录 | 决策依据随对话丢失；AI 编码助手无上下文可依；同一问题反复争论 |
| 外部 Wiki（Confluence/语雀等） | 独立开发引入额外运维负担；文档应与代码同仓库、同提交、同演进 |
| 仅保留 walkstreet/docs 等模块级文档 | 无法承载跨模块的架构决策与计划跟踪；无统一索引等于没有索引 |

## 后果

- 正面：研发计划、设计思路、需求、测试可追溯；AI 编码助手可直接以文档为上下文输入，产出与设计对齐
- 负面：增加每次改动的心智负担，靠"登记一条索引"的成本换取长期可维护性
